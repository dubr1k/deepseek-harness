# Обновление нашей сборки DSH

Публикуемый комплект находится в `local-distribution/` ветки `release/codex-integrations` GitHub-форка `dubr1k/deepseek-harness`. Исходники ядра в корне соответствуют закреплённой базе; обновления интеграций не требуют пересборки подписанного приложения.

1. При выходе нового DSH изучить официальный релиз, изменения API и миграции профиля. Зафиксировать версию, URL, контрольную сумму и подпись приложения. Повторить проверку подписи после установки комплекта и запуска MCP; встроенный Python запускать с `-B`, чтобы не перезаписать подписанные `.pyc`. Создать ветку `update/dsh-<version>` от текущей ветки комплекта.
2. Сохранить прежнее приложение, архив и тег и резервную копию профиля. Использовать отдельный тестовый профиль; не ставить кандидата поверх рабочей версии без готового отката. Не переносить старые экспериментальные изменения ядра автоматически.
3. Проверить реальный граф peer dependencies Codex против нового runtime, включая pi-ai. Обновить снимок исходников Codex в `sources/` и установочный tgz в `payload/` совместно; зафиксировать commit в versions.json. Собрать и запустить целевые тесты. Удалить внешний `dsh-subagent-codex` из зависимостей и bundles профиля: даже отключённый пакет может подменять штатные пакеты. Нативные роли сохранить.
4. Проверить актуальность Creator Inspect hotfix; убрать его из кандидата только если штатное исправление подтверждено настоящим Creator-сценарием. Собрать Project Passport, Workspace tools и Task templates; обновить plugins.json и versions.json.
5. Выполнить реальную приёмку: запрос к Codex; квоты/Fast; четыре нативные роли; Creator создаёт тестовый плагин; Firecrawl возвращает страницу; Graphify CLI/существующий граф доступны; Project Passport рендерит AGENTS.md; Workspace tools запускает проверки и нативного ревьюера, сохраняет/открывает/экспортирует записи после перезапуска. Проверку извлечения Graphify выполнять только по явному запросу. OpenDesign проверять отдельно при доступном CLI и авторизации. Не выдавать конфигурацию за работающую интеграцию.
6. Обновить evidence с точными версиями, результатами и ограничениями, README, hashes. Просмотреть исходящие файлы на секреты и личные данные. Проверить архив в отдельном каталоге; не изменять активные проекты тестами.
7. Только после приёмки обновить ветку комплекта и выпустить тег `stable-YYYY.MM.DD[-N]` с DMG/ссылкой, архивом интеграций и SHA256SUMS. Сверить SHA удалённой ветки и ссылки релиза. Предыдущий проверенный релиз сохранить для отката.

Если кандидат не прошёл совместимость или реальные сценарии, он остаётся кандидатом; текущая стабильная версия не меняется. Новые upstream-релизы сами по себе не являются разрешением на автоматическую установку на рабочую машину.
